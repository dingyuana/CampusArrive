## 1 项目概述

### 1.1 项目命名

本项目正式命名为「微迎新」，英文名 **CampusArrive**，寓意新生顺利抵达校园、轻松完成报到。本文档体系内所有项目名称、文档编号（项目代号 `CA`）与对外品牌均统一使用该命名。在工程代码仓库、容器镜像、小程序应用名等工程资产中，英文名 `campus-arrive` 作为统一标识符；在面向师生的产品界面与宣传材料中，以中文名「微迎新」为主展示。

### 1.2 项目背景

微迎新（CampusArrive） v1.0 已于上一迎新季上线运行，承担新生从入校到完成报到的全流程线上化任务。v1.0 覆盖五项核心能力：报到流程指引、校园导航、报到进度追踪、学校自主流程配置、新生/辅导员/管理员三端协作。其中校园导航通过后端 MCP（Model Context Protocol，模型上下文协议）集成高德地图实现路径与点位服务。v1.0 上线后有效缩短了现场排队与人工咨询时间，但在智能化答疑、特殊群体可达性、家长信息获取、跨系统数据贯通与合规治理方面仍有明显缺口。

v1.1 作为快速迭代版本，在 v1.0 稳定底座上新增五大模块：AI 迎新智能助手、无障碍访问改造、家长查看端、系统集成中间件、安全与合规保障。本次迭代不重构 v1.0 既有功能，以增量交付、低侵入集成为原则，目标是在 6 周内完成开发、测试、安全合规评估并上线，服务下一个迎新季。

### 1.3 项目目标

本次迭代聚焦业务价值与合规底线两类目标。

业务目标：

- 以 AI 智能助手承接新生高频咨询，降低辅导员人工答疑负荷，将重复性咨询占比显著压缩；
- 通过 WCAG 2.2 AA 级无障碍改造，使视障、听障、操作受限等特殊群体新生可独立完成报到；
- 开放家长查看端，让家长在无需登录学生账号的前提下了解报到进度，缓解家长焦虑与代查压力；
- 以系统集成中间件打通报到系统与教务、宿管等老旧业务系统，消除数据孤岛与手工搬运；
- 建立覆盖数据、模型、应用三层的安全合规体系，满足国家与教育行业现行法规标准要求。

约束目标：

- 迭代周期 6 周，团队规模 6 人（后端 2、前端 2、测试 1、DevOps 1）；
- 校园内网 Docker 容器化部署，学生数据不出校；
- 年度运行成本控制在约 5600 元区间。

### 1.4 痛点解决

| 痛点 | 现状表现 | v1.1 解决方式 |
| --- | --- | --- |
| 新生咨询量集中、辅导员重复应答 | 报到季辅导员每日应对大量同质化提问，挤占事务性工作时间 | AI 智能助手基于校园知识库 RAG 检索，7×24 小时即时作答，标准流程为主、对话为辅 |
| 特殊群体新生操作困难 | 视障/色弱/操作受限学生难以使用小程序界面 | 按 WCAG 2.2 AA 级改造，提供读屏、键盘可达、对比度与焦点可见性支持 |
| 家长信息获取渠道缺失 | 家长只能反复电话询问或借用学生账号，信息滞后且存在账号共享风险 | 家长查看端以轻量 H5 提供只读进度视图，授权脱敏、不触碰学生完整隐私 |
| 跨系统数据手工搬运 | 报到数据需人工导入教务、宿管等系统，易错且滞后 | 系统集成中间件通过 API 网关与 CDC 实现准实时数据同步 |
| 合规基线缺失 | v1.0 未系统化对标个人信息保护与生成式 AI 安全要求 | 安全与合规保障模块对标 PIPL、等保 2.0、GB/T 45654-2025、JY/T 0661-2025、OWASP Top 10 |

## 2 项目范围

### 2.1 v1.0 已交付清单

v1.0 为本次迭代的基线，其交付物纳入运维与兼容性保障范围，不在 v1.1 重复开发：

- 报到流程指引：分步骤引导新生完成线上报到环节；

本次迭代的边界由五大模块界定，凡未列入下表的诉求均视为范围外，纳入 v1.2+ 评估。

| 模块 | 范围内 | 范围外（不纳入 v1.1） |
| --- | --- | --- |
| AI 迎新智能助手 | MaxKB 知识库构建、RAG 检索、DeepSeek V4 对话、小程序双层交互、对话日志与审计 | 多轮复杂任务编排、自定义模型微调、跨校知识共享 |

| 家长查看端 | 轻量 H5 进度查看、授权绑定、脱敏展示 | 家长端缴费、家长端消息互动 |
| 系统集成中间件 | API 网关、RabbitMQ 消息队列、Debezium CDC 数据同步、与教务/宿管系统对接 | 全校统一数据中台、实时数仓建设 |

### 2.3 v1.2+ 远期规划

v1.1 上线后，依据实际运行数据与校方反馈，远期可演进方向包括：

- AI 能力深化：多轮任务编排、迎新数据智能分析与画像、辅导员工作台 AI 辅助；
- 无障碍扩展：全三端无障碍达标、手语/语音多模态交互；
- 家长端增强：缴费提醒、家校通知、家长满意度调研；
- 集成深化：统一数据中台、与一卡通/图书馆/财务系统贯通；
- 合规进阶：等保三级正式测评、数据出境与跨校共享治理。

远期规划仅作方向性指引，不构成 v1.1 承诺，具体范围在后续版本立项时另行确定。

## 4 五大模块概述

### 4.1 AI 迎新智能助手

目标：以智能对话承接新生高频咨询，降低辅导员重复答疑负荷，同时保持标准流程的主导地位。

技术方案：采用 MaxKB v1.10 LTS 开源平台构建校园迎新知识库并编排工作流；对接 DeepSeek V4 大模型提供自然语言生成能力，部署于校园内网，新生问答数据全程不出校。学生前端采用"标准流程为主、RAG 对话为辅"的双层交互模式：新生优先沿既定报到流程操作，遇疑问时唤起对话，助手基于知识库检索作答，必要时通过 MCP 调用 v1.0 既有能力（如校园导航、进度查询）完成工具化应答。

关键交付物：

- 校园迎新知识库（含问答对、流程文档、政策口径）及维护手册；
- MaxKB + DeepSeek 内网部署与对接方案；
- 小程序对话入口与双层交互流程；
- 对话日志、审计与敏感词过滤机制；
- 助手答复准确率与人工接管率评估报告。

### 4.2 无障碍访问改造

目标：使特殊群体新生能够独立、顺畅地完成报到操作，达到 WCAG 2.2 AA 级合规。

技术方案：依据 WCAG 2.2 的可感知、可操作、可理解、健壮性四大原则，对小程序与家长端进行改造，重点落实文本替代、键盘可达、焦点可见、对比度达标、表单标签关联、错误提示明确等要求；改造同步建立无障碍自测流程，纳入测试环节。

关键交付物：

- 无障碍改造清单与 WCAG 2.2 AA 级对标矩阵；
- 改造后的前端组件与样式规范；
- 读屏、键盘、对比度等场景的测试用例与自测报告；
- 无障碍持续维护指引。

### 4.3 家长查看端

目标：为家长提供轻量、安全的报到进度查看入口，无需登录学生账号即可了解关键节点。

技术方案：以轻量 H5 页面实现，通过家长授权绑定建立与学生报到进度的关联视图；展示内容做脱敏处理，仅呈现进度节点与必要提示，不暴露学生完整隐私字段；访问链路经 API 网关统一鉴权。

关键交付物：

- 家长端 H5 页面与授权绑定流程；
- 脱敏展示规则与权限控制说明；
- 家长端与后端进度数据的接口契约；
- 家长端无障碍适配（随 4.2 一并达标）。

### 4.4 系统集成中间件

目标：打通报到系统与教务、宿管等老旧业务系统，消除数据孤岛与人工搬运，支撑准实时数据同步。

技术方案：以 Spring Cloud Gateway 作为统一 API 网关，承担路由、鉴权、限流与协议适配；以 RabbitMQ 消息队列实现异步解耦与事件通知；以 Debezium CDC（Change Data Capture）捕获报到系统数据库变更，向下游系统准实时同步，避免对老旧系统做侵入式改造。

关键交付物：

- API 网关路由、鉴权与限流配置；
- 消息队列主题/队列设计与事件契约；
- Debezium CDC 同步链路与数据一致性校验方案；
- 与教务、宿管系统的对接接口与联调记录；
- 中间件部署与监控方案。

### 4.5 安全与合规保障

目标：建立覆盖数据、模型、应用三层的安全合规基线，满足国家与教育行业现行法规标准，作为本次迭代上线的前置条件。

技术方案与对标：

- 《中华人民共和国个人信息保护法》（PIPL）：落实最小必要、告知同意、脱敏存储原则；
- 网络安全等级保护 2.0（等保 2.0，GB/T 22239-2019）：开展定级自测评与安全加固；
- GB/T 45654-2025《网络安全技术 生成式人工智能服务安全基本要求》：作为我国首个生成式 AI 服务安全国标及《生成式人工智能服务管理暂行办法》的配套技术文件，指导 AI 助手的内容安全、训练数据与模型服务安全评估；
- JY/T 0661-2025《教育数据分类分级指南》：依据教育部该标准对新生报到相关教育数据分类分级，落实《数据安全法》在教育领域的要求；
- OWASP Top 10：针对 Web/小程序常见风险进行注入、失效访问控制、安全配置错误等加固。

关键交付物：

- 数据分类分级目录与脱敏规则；
- 个人信息保护影响评估（PIPIA）报告；
- 生成式 AI 服务安全自评估报告（对标 GB/T 45654-2025）；
- 等保 2.0 自测评与加固清单；
- OWASP Top 10 安全测试报告与修复记录；
- 安全合规上线检查单（Go/No-Go 依据）。

## 6 验收标准与上线门槛

### 6.1 上线门槛（前置条件）

安全合规为本次迭代上线的前置条件，未通过下列检查项不得进入上线流程：

- 数据分类分级目录完成并经校方信息中心确认；
- 个人信息保护影响评估（PIPIA）通过评审；
- 生成式 AI 服务安全自评估对标 GB/T 45654-2025 完成，无高危项遗留；
- 等保 2.0 自测评无高危风险，中危风险有明确整改计划；
- OWASP Top 10 安全测试无高危漏洞；
- 安全合规上线检查单全部勾选通过。

### 6.2 模块验收标准

| 模块 | 验收标准 |
| --- | --- |
| AI 迎新智能助手 | 知识库覆盖迎新高频问题；答复准确率达到约定阈值；双层交互流程可用；对话日志与审计完整；数据不出校验证通过 |
| 无障碍访问改造 | 小程序与家长端通过 WCAG 2.2 AA 级自测；读屏、键盘、对比度场景用例通过 |
| 家长查看端 | 授权绑定流程可用；进度展示脱敏且与实际一致；经网关鉴权访问；无障碍达标 |
| 系统集成中间件 | 网关路由与鉴权生效；消息队列收发正常；CDC 同步延迟与一致性达标；与教务/宿管联调通过 |
| 安全与合规保障 | 第 6.1 节前置条件全部通过；安全合规上线检查单签批 |

### 6.3 验收流程

验收分模块自测、集成测试、安全合规评估、整体验收四阶段。整体验收由项目经理组织，校方信息中心、辅导员代表与开发团队共同参与，验收结论与遗留问题清单形成书面记录，作为上线依据。

| 安全合规不达标 | 上线 | 中 | 高 | 合规工作前置并行，不作为末道工序；以 GB/T 45654-2025、JY/T 0661-2025 为基线持续自检；设安全合规 Go/No-Go 门槛 |

风险跟踪机制：风险登记册由项目经理维护，每周例会复盘状态变化，新增或升级风险即时通报校方信息中心。

## 8 项目组织架构与职责分工

### 8.1 组织架构

项目在校方信息中心授权下运作，由项目经理统筹交付，技术负责人把握架构与风险，安全合规负责人守合规底线。

- 项目发起人：校方信息中心负责人，授权立项、审批章程与重大变更、验收上线；
- 项目经理：统筹范围、进度、成本与干系人沟通，对交付负责；
- 技术负责人/架构师：把握整体技术方案与架构决策，主导难点攻关；
- 开发团队：后端 2 人、前端 2 人，按模块分工交付；
- 测试工程师 1 人：负责功能、无障碍与安全测试；
- DevOps 工程师 1 人：负责部署、CI/CD、监控与 MaxKB/DeepSeek 内网部署；
- 安全合规负责人：统筹数据分级、隐私保护与合规自评估，把控上线门槛。

### 8.4 治理机制

- 章程授权：本章程签署即授权项目组在范围内开展交付；

- 回顾改进：迭代结束召开回顾会，沉淀经验并输入 v1.2+ 规划。
