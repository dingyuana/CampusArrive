# 微迎新（CampusArrive） v1.1 开发排期与里程碑

> 版本：v1.1.0 ｜ 排期周期：6 周（快速迭代）｜ 文档状态：基线发布
> 适用范围：AI 迎新智能助手、无障碍访问改造、家长查看端（H5）、系统集成中间件、安全与合规保障
> 团队规模：6 人（后端 2、前端 2、测试 1、DevOps 1）

---

## 0. 文档说明

本文档为「微迎新（CampusArrive） v1.1」6 周快速迭代的开发排期基线，明确五大并行模块的任务分解、人力投放、关键路径、Go/No-Go 决策点、安全合规节奏与灰度发布策略，作为研发、测试与运维协同的统一依据。

**阅读约定**

- 周次标记为 `W1`～`W6`，每周按 5 个工作日计，团队满编产能为 **30 人天/周**，6 周总产能 **180 人天**。
- 表格中符号：`█`＝主力开发/核心交付；`▒`＝联调/优化/支持；`◇`＝设计/环境/准备；`✓`＝验收/审计/上线；`—`＝无任务或等待。
- 关键路径任务以 **加粗** 标注。

## 4. 关键路径分析

### 4.1 关键路径定义

本迭代关键路径为 **AI 迎新智能助手 + 系统集成中间件** 双线并行汇合链路，二者构成最长依赖链，任一环节滑期将直接推迟正式发布。

```
W1 环境/对接验证 ──► W2-3 AI 开发 + 中间件开发 ──► W4-5 联调优化 ──► W6 集成测试 + 灰度
   (Go/No-Go #1)         (Go/No-Go #2)                  (Go/No-Go #3)        (Go/No-Go #4)
        │                       │                              │                    │
   MaxKB/DeepSeek          知识库/工作流/MCP              AI↔中间件联调         全链路+压测+渗透
   网关/MQ 环境            路由/事件链/CDC                 稳定性加固            灰度部署
```

**关键路径任务序列（不可压缩）**

1. W1：MaxKB 部署 + DeepSeek 对接验证 → 决定 AI 方案可行性
2. W2–W3：知识库/工作流/MCP + 网关/事件链/CDC + AI 安全护栏 → 决定核心链路可用性
3. W4–W5：AI 与中间件联调优化、稳定性加固 → 决定下游家长端/无障碍可集成
4. W6：全链路测试 + 压测 + 渗透 + 灰度 → 决定正式发布

### 4.2 依赖关系与浮动时间

| 路径 | 依赖说明 | 浮动时间（Slack） | 风险等级 |
|---|---|---|---|
| **AI 助手 + 中间件（关键路径）** | 串行依赖最紧密，里程碑硬约束 | **0 周**（无浮动） | 高 |
| 家长端 H5 | 依赖 API 契约（W1）+ CDC 视图稳定（W3 末），可用 Mock 提前并行 | ~1 周 | 中 |
| 无障碍改造 | 依赖主端功能基本稳定（W4 起），但组件级改造可前置 | ~1 周 | 中 |
| 安全合规 | 贯穿全周期，PII/护栏受 AI/中间件进度约束 | 0～0.5 周 | 高（M2 硬约束） |

### 4.3 关键路径风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| DeepSeek 对接不达预期（W1） | AI 方案返工，关键路径起点延误 | W1 设 Go/No-Go；预案：降级为本地模型或多供应商兜底 |
| CDC 数据同步链路复杂度高（W3） | 中间件核心链路无法跑通 | W2 提前做 CDC PoC；简化首版同步范围，分批接入 |
| AI 安全护栏与功能耦合（W3） | M2 无法验收 | 护栏与功能并行开发，护栏作为独立中间层，解耦验收 |
| W6 压测/渗透暴露重大缺陷 | 推迟灰度与发布 | W4–W5 提前介入冒烟压测与安全自查，预留 W6 修复窗口 |

## 5. Go/No-Go 决策点定义

每个决策点需明确**验收准则、决策人、决策时点、No-Go 应对**。决策结果记入里程碑评审纪要。

### 决策点 #1 — AI 对话验证（W1 末 · M1）

| 项 | 内容 |
|---|---|
| 验收准则 | DeepSeek + MaxKB 端到端可完成多轮问答；响应时延 P95 ≤ 5s；知识库可加载并检索；MCP 工具调用链路可打通（可仅 1 个工具） |
| 决策人 | 项目负责人 + 后端-AI + DevOps |
| 决策时点 | W1 第 5 个工作日 |
| Go 则 | 进入 W2 AI 开发，按原排期推进 |
| No-Go 则 | 启动备选方案（多供应商兜底/本地模型）；AI 排期重估，压缩非关键模块投入支援；必要时向项目负责人升级 |

### 决策点 #2 — 集成中间件核心链路 + AI 安全护栏（W3 末 · M2）

## 7. 灰度发布策略（三阶段灰度）

灰度发布在 W6 执行，遵循「内部 → 单校 → 双校」三阶段递进，每阶段设入口准则、监控指标、回滚条件与退出准则。

### 7.1 灰度阶段总览

| 阶段 | 时段 | 流量/范围 | 目标 | 退出准则 |
|---|---|---|---|---|
| 灰度一：内部预生产 | W6 D1–D2 | 内部用户 + 模拟数据，100% 内部 | 验证全链路、监控、回滚预案 | 全链路无 P0/P1 缺陷；监控齐备；回滚演练通过 |
| 灰度二：单校小范围 | W6 D3–D4 | 1 所试点高校，限定院系/专业，5%–20% 流量 | 验证真实数据与业务闭环 | 业务功能正常；无安全告警；用户反馈可控 |
| 灰度三：双校扩展 | W6 D5+ | 扩展至 2 所试点高校，全量该校新生 | 验证规模与稳定性 | 性能达标；无重大缺陷；试点高校验收确认 |

### 7.2 各阶段细则

**灰度一：内部预生产灰度（W6 D1–D2）**

- 入口准则：决策点 #4 Go；预生产环境与生产配置一致；监控大盘、日志、告警就绪。
- 监控指标：全链路请求成功率、AI 问答 P95 时延、MQ 消息积压、CDC 同步延迟、错误率。
- 回滚条件：出现 P0 缺陷、安全告警、数据不一致，立即回滚至 v1.0 稳定版。
- 退出准则：连续 2 个工作日无 P0/P1 缺陷；监控齐备；回滚预案演练通过。

**灰度二：单校小范围灰度（W6 D3–D4）**

- 入口准则：灰度一退出准则全部满足；试点高校数据准备就绪；运营/客服对接完成。
- 流量策略：按院系/专业灰度，5% → 10% → 20% 递进，每档观察 ≥4 小时。
- 监控指标：真实业务成功率、家长端 H5 可用性、无障碍可用性、AI 问答准确率、用户反馈工单。
- 回滚条件：业务功能异常、安全事件、数据泄露迹象、负面反馈集中，回滚并保留现场。
- 退出准则：业务闭环正常；无安全告警；用户反馈可控；试点高校对接人确认。

**灰度三：双校扩展灰度（W6 D5+）**

- 入口准则：灰度二退出准则满足；扩容与限流配置就绪；压测结论支持规模扩展。
- 流量策略：扩展至第 2 所试点高校，全量该校新生，按校分批接入。
- 监控指标：并发性能、资源水位、稳定性指标、跨校数据隔离正确性。
- 回滚条件：性能不达标、资源瓶颈、数据隔离异常，按校粒度回滚。
- 退出准则：性能达标（支持 10000 并发）；无重大缺陷；两所试点高校验收确认 → 转为正式发布。

### 7.3 回滚与应急

- 回滚单位：按「灰度阶段 + 高校」二维粒度回滚，支持单校回滚不影响他校。
- 回滚时效：发现 P0/P1 问题后 **15 分钟内** 决策、**30 分钟内** 完成回滚。
- 数据处理：灰度期间产生的数据须明确保留/清理策略，避免回滚后数据不一致。
- 应急联络：建立灰度期间 7×12 应急群，DevOps + 测试 + 各模块 oncall。
